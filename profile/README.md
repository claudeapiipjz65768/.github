<h2>一、接入点选择：环境变量、客户端参数还是自建网关</h2>
<p>三种接法的差别不在能不能通，而在改配置的成本和可观测性。先用最简单的，等出现多项目、多出口的需求再升级，能少走很多弯路。</p>
<h3>环境变量：单机、单项目首选</h3>
<p>设置 HTTPS_PROXY 与 HTTP_PROXY 两个变量，多数 HTTP 客户端会自动读取。优点是改一行就生效，缺点是对进程内不同请求无法区分出口，多项目共存时会互相覆盖。</p>
<h3>客户端显式传参：多出口并行时用</h3>
<p>在构造客户端时传入代理配置，不同实例用不同出口，互不影响。Python 生态里常见做法是给底层 HTTP 客户端传 proxies 字典，或直接传 proxy 参数；流式场景下要确认底层走的是同一条通道，否则会出现"普通请求走代理、流式请求直连"的错配。</p>
<h3>自建网关：需要统一鉴权与审计时用</h3>
<p>在中间放一层轻量代理网关，统一做出口选择、密钥注入、日志记录和限流。好处是上游业务代码零改动，坏处是多一个故障点，要自己保证网关本身的高可用。</p>

<h2>二、鉴权：白名单和账号密码各有各的坑</h2>
<p>两种方式经常被当成等价的开关，其实对运维的影响完全不同。白名单依赖源地址稳定，账号密码依赖凭据管理，选错会让后续排障变得很别扭。</p>
<h3>白名单：省事但怕源地址变动</h3>
<p>把服务器的出口地址登记到供应商侧，请求就不用带凭据。风险在于源地址可能变：换机房、加节点、走 NAT 出口、或者云主机的弹性地址漂移，都会让请求突然被拒。建议在变更流程里加一步"同步白名单"，并在客户端对 407 做单独告警。</p>
<h3>账号密码：灵活但要防泄漏</h3>
<p>凭据写在配置文件或密钥管理服务里，不要硬编码进仓库。轮换周期建议与人员变动挂钩；多人共用同一组凭据时，出问题无法定位到人，最好一个项目一组。</p>

<h2>三、超时：三个数字分开设，别只写一个总时长</h2>
<p>把超时写成 60 秒这种单值，等于放弃了定位能力。连接、读取、写入三个阶段的问题表现完全不同，分开设才能从日志里看出卡在哪。</p>
<h3>连接超时给 5 秒</h3>
<p>代理地址可达性正常时，TCP 握手通常在 1 秒内完成。5 秒还没连上，基本可以判定线路或白名单有问题，继续等没有意义。这一项设短，能让故障快速暴露。</p>
<h3>读取超时按任务类型分档</h3>
<p>普通同步请求给 60 秒，长文档生成给 120 至 180 秒，流式输出则要看两段：首字节等待和数据块间隔。流式场景里更实用的做法是设"首个数据块 20 秒、块间隔 30 秒"，比一个总时长更容易定位断流。</p>
<h3>连接池等待也要设上限</h3>
<p>并发打满时，新请求会在池里排队。这个等待如果不设上限，会表现为"请求迟迟不发出，日志里却什么都没有"。给 3 至 5 秒，超时直接失败并记录，比无声排队好排查。</p>

<h2>四、重试：只重试该重试的，次数别超过 2 次</h2>
<p>重试是最容易把成本放大的参数。正确做法是按状态码分类，配合指数退避和随机抖动，并且严格限制次数。</p>
<h3>哪些该重试，哪些不该</h3>
<p>429 限流、500、502、503 以及服务端过载类状态码可以重试；400 参数错误、401 鉴权失败、403 权限不足、404 路径错误不要重试，重试只会浪费配额。代理侧返回的 407 也要区分：凭据错就别重试，白名单未生效可以重试一次。</p>
<h3>退避曲线与抖动</h3>
<p>常见做法是 1 秒、2 秒、4 秒递增，每次叠加 0 至 500 毫秒随机抖动，避免所有客户端在同一时刻重发形成尖峰。总重试次数控制在 2 次以内，也就是一次原始请求加两次重发。流式请求要更保守：只在尚未收到任何数据块时重试，一旦开始输出就改为向上层报错，否则已消耗的 token 要再付一遍。</p>

<h2>五、请求头与上线验证：细节决定排障难易</h2>
<p>代理只管转发，请求头仍然是你的客户端生成的。头信息不一致时，问题往往表现为"偶发的鉴权失败"或"偶发的参数错误"，很难第一时间想到是头的问题。配置改完直接压生产也一样，会让参数问题和线路问题混在一起，分不清先后。</p>
<h3>版本头、转发头与压缩编码</h3>
<p>调用消息接口时带上接口版本头与 JSON 内容类型，版本号写死而不是每次动态取，避免上游更新后行为漂移。不要顺手加 X-Forwarded-For 这类转发头去让链路"看起来更真实"，既没有稳定收益，也会让日志失真、排障困难。压缩与编码保持客户端默认协商即可，手动关掉压缩会让长响应体的传输时间在跨境线路上明显变长。</p>

<p>配置改完不要直接压生产。按"出口地址、真实接口、小并发"三步走，每步都能独立定位问题，比一次性跑全链路更容易找出错在哪。三步都过之后再逐步放量，每次只改一个变量。</p>

<h3>先确认出口地址对不对</h3>
<p>用 curl 带上代理访问一个回显地址的接口，确认返回的地址与你购买的出口一致、归属地与预期相符；再跑一次不带代理的直连做对照，排除"以为走了代理其实没走"。</p>
<h3>再打一次真实接口并计时</h3>
<p>用 curl 的 -w 参数输出连接、握手、首字节三个时间点，同时在服务端日志里核对请求是否到达。返回体只要求 16 个 token，够验证链路又不浪费额度。三项时间点里哪段异常，就去调对应的超时参数。</p>
<h3>最后压一轮小并发</h3>
<p>用 10 至 20 并发跑三分钟，观察错误码分布和重试次数。这一步能暴露连接池、端口上限和限流阈值的问题，是放量前最有价值的一次测试。</p>

<h2>常见问答</h2>
<h3>代理能不能多层串联？</h3>
<p>答：技术上可以，但每多一层就多一次握手和一处可能的故障。除非有明确的合规或网络架构要求，建议只保留一层出口，把复杂度放在监控上而不是链路上。</p>
<h3>流式输出总是中途断开，先查什么？</h3>
<p>答：先看中间设备是否回收空闲连接，把心跳间隔压到 30 秒左右试一次；再看读取超时是不是按总时长设的，改成首块与块间隔分别计；最后才考虑换出口。</p>
<h3>重试次数设成 5 次是不是更稳？</h3>
<p>答：未必。服务端限流时，多次重试会让拥塞更严重，成本也成倍上升。多数场景 2 次足够，把省下的精力放在退避曲线和错误分类上，收益更明显。</p>
<h3>白名单和账号密码能同时开吗？</h3>
<p>答：可以，而且生产环境建议这样做。白名单限制来源，凭据限制使用者，两者叠加后即使凭据外泄，非白名单来源也用不了。代价是配置项变多，需要把两处变更写进同一份流程。</p>
